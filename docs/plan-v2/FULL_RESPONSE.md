### 首先修正对命题的理解

找到的 openKylin 官方命题全文，不仅要求问答评测，还明确要求组织**对话、记忆记录、行动轨迹、文件证据**，覆盖**长期保持、记忆调用、动态更新、相近区分、边界识别、任务复用**。演示要求是在 **openKylin 桌面上，对至少两款智能体进行评测，输出雷达图，录制 3–5 分钟完整视频**；`.deb` 是建议项，不是比真实接入更重要的硬门槛。([bbs.openkylin.top](https://bbs.openkylin.top/t/topic/173541))

因此，**六种自制 memory baseline 不等于六款真实智能体，也不能自动满足“两款智能体”的演示要求。**

### 初赛只抓住四件事

| 优先级 | 初赛必须形成的证据 | 不要用什么替代 |
|---|---|---|
| P0：评分可信 | 修复已发现的评分漏洞，保留证据与错误原因，完成一轮人工—裁判校准 | 再增加漂亮指标 |
| P0：数据可信 | 一套冻结、可审查、包含自然表达和生命周期变化的小数据集 | 大量未经核对的 LLM 生成文本 |
| P0：真实接入 | 在 openKylin 上运行两款真实智能体，验证跨会话记忆与文件任务 | 两个模型、两个 mock 或两个自制键值存储 |
| P0：可复现交付 | 原始结果、版本清单、一键 CLI、PDF、真实录屏 | 只有截图、只有平均分、只有计划 |

**建议规模：**保留原版 120 题离线诊断；新增 **60 个独立故事，12 个开发、48 个测试，每个两种等义表达，共 96 个正式测试问答**；从中选择 **12 个故事**评测两款真实智能体。这个规模仍不足以支撑普遍性排名，但足以做一个诚实、有区分度的初赛研究原型。

**建议定位：**

> MemoBench 是面向 openKylin 智能体的证据驱动记忆回归评测工具，检查智能体是否在新会话中正确保留、更新、隔离和使用历史信息，并通过实际任务产物验证“记住了”是否真正转化为“做对了”。

**这两天不要做：**重造记忆服务、部署图数据库、训练模型、追求百万 token、搭建完整排行榜网站、同时复现所有论文、申请独立 SIG、承诺软件商店上架。

# A. 深度调研与项目定位

## A1. 先分清：这些工作不是同一种“记忆 Benchmark”

可以把相关研究分成四类：

**长上下文读取**研究“所有资料已经放进输入，模型能否找到答案”；**长期对话记忆**研究“跨会话的信息能否保存、检索和更新”；**持续状态与个性化**研究“当前到底什么还有效、什么已经变了”；**智能体执行评测**进一步检查“历史信息是否影响后续工具调用和任务结果”。

MemoBench 当前主要处于第二类的**受控合成诊断**阶段。值得深化的方向是第二类到第四类之间的工程连接，而不是重新发明已有的“更新、拒答、隐式偏好”概念。

### 主要基准比较

下表的“局限”是相对于你的项目目标而言，不表示这些工作本身质量不高。

| 基准／工作 | 主要能力 | 数据如何构造 | 主要指标 | 局限与对 MemoBench 的启示 |
|---|---|---|---|---|
| **LongMemEval，ICLR 2025** | 信息提取、跨会话推理、时间推理、知识更新、拒答 | 人工编写问题和证据，LLM 模拟证据会话后人工编辑，再加入无关会话扩展历史 | LLM 判断问答正确性；可观察检索时计算 Recall@k、NDCG@k | 六个问答维度不是你的独创。应借鉴证据标注、按题型评分及裁判校准，而不是复制大规模长历史。([arxiv.org](https://arxiv.org/html/2410.10813v2)) |
| **LoCoMo，ACL 2024** | 单跳、多跳、时序、开放域、对抗问答；事件总结与多模态对话 | 人物设定和事件结构驱动生成长期对话，辅以人工校验 | 原始 QA 主要使用答案 F1；另有总结与多模态任务指标 | 后续系统论文常改用 LLM judge，数字不能直接和原始 F1 横比。它侧重长期对话，不是 openKylin 软件回归规范。([aclanthology.org](https://aclanthology.org/2024.acl-long.747/)) |
| **MSC，ACL 2022** | 多次会话中的人物信息利用、持续对话与个性化 | 众包人员扮演人物，进行多会话交流，并提供历史摘要 | 困惑度；人工评价历史话题引用、互动质量和整体评分 | 更接近持续对话质量评估，而不是精确的状态更新、删除与任务执行判定。不能简单把回答流畅等同于记忆正确。([arxiv.org](https://arxiv.org/html/2107.07567)) |
| **MemoryBank，2023／AAAI 2024** | 历史回忆、用户画像、长期陪伴及记忆衰减 | 合成人物和中英文多日对话，人工编写探测问题 | 检索准确率、回答正确性、上下文连贯性及模型排序分数 | **首先是记忆系统及其评测方案，不是与 LongMemEval 完全同类的独立通用基准。**自然衰减也不等于用户要求删除。([arxiv.org](https://arxiv.org/html/2305.10250)) |
| **PerLTQA，2024** | 语义／情景记忆分类、检索、答案综合 | 人物、社会关系、事件、历史对话以及生成问答；标注记忆锚点 | 分类 P/R/F1/Accuracy、Recall@K、记忆锚点 MAP、LLM 正确性／连贯性 | 很值得借鉴“证据锚点”。但数据许可与代码许可必须分别检查，不能直接纳入木兰许可证数据包。([arxiv.org](https://arxiv.org/html/2402.16288v1)) |
| **MemBench，2025** | 事实记忆、反思性记忆、跨会话综合、更新与时序 | 基于关系、偏好等数据构造用户及交互，包含参与者／观察者视角 | 选择题准确率、证据检索召回、容量与处理效率 | “个人偏好”“反思”“参与者视角”都已有前作。闭集评分有可复现优势，但不能完全替代开放式智能体任务。([arxiv.org](https://arxiv.org/html/2506.21605v1)) |
| **DialSim，2024／ICLR 2025** | 长期多方对话理解、随时间变化的事实、实时应答 | 基于电视剧对话组织多角色历史，生成探测问题，使用实体替换等处理 | **时间限制内准确率**，以及重复实验均值、标准差 | 说明延迟和记忆维护时间应进入评测；但影视对话不等于真实操作系统使用，文本许可和预训练污染也需注意。([arxiv.org](https://arxiv.org/html/2406.13144v2)) |
| **LongBench，2023；LongBench v2，2024–2025** | 长文档问答、对话总结、检索；v2 包含长对话历史理解 | 汇集多类长上下文任务；v2 使用人工设计的较难选择题 | 原版按任务使用 F1、ROUGE、准确率等；v2 主要选择题准确率 | 主要评估一次输入中的长上下文理解，不等同于跨会话持久记忆的写入、更新和删除。可作为读取器能力参考。([arxiv.org](https://arxiv.org/abs/2308.14508)) |
| **MemoryAgentBench，2025，2026 有修订** | 准确检索、测试时学习、长程理解、选择性遗忘 | 将长上下文数据转换为增量交互，并补充针对性任务 | 各子任务的问答／分类／冲突处理表现 | 必须核对“选择性遗忘”具体测的是什么，不能自动理解为隐私删除。适合借鉴流式输入与能力拆解。([arxiv.org](https://arxiv.org/abs/2507.05257)) |
| **PersonaMem 系列，2025–2026** | 动态偏好、隐式偏好、个性化回应；v3 扩展到跨平台推荐、主动性和工具任务 | v1/v2 以人物和历史模拟为主；v3 用真实行为信号作为基础构造跨平台数字生活 | 早期包含选择式评估；v3 使用开放式、任务相关的个性化评测规范 | 隐式偏好和跨平台行动也不是空白。可借鉴“何时不该个性化”，但不要照搬其庞大数据工程。([arxiv.org](https://arxiv.org/abs/2504.14225)) |
| **BEAM，2025–2026** | 超长交互中的长期记忆与多种推理能力 | 生成连贯的超长对话，覆盖百万乃至更长 token 规模 | 多能力正确性与效率分析 | 对你而言是规模参照，不是初赛复现目标。长到运行不起，并不会自动提高比赛价值。([arxiv.org](https://arxiv.org/abs/2510.27246)) |
| **EverMemBench，2026** | 细粒度回忆、约束意识、主动性、知识更新、用户画像 | 多人、多群组、长期项目情境；结合结构化事件与生成内容，做自动和人工校验 | 事实题语义判分；部分意识／画像任务使用选择式评估 | 比简单双人聊天更丰富，但仍不能直接替代真实系统动作和文件结果。可借鉴 evidence-only 对照，分离检索与推理失败。([arxiv.org](https://arxiv.org/html/2602.01313v1)) |
| **AMA-Bench，2026** | 智能体历史中的回忆、因果推断、状态更新、抽象 | 真实智能体轨迹加专家问题，以及可扩展的合成轨迹 | LLM 判定正确性及 F1，并做人工元评估 | **“评估行动轨迹”已有明确前作。**你的贡献应是 openKylin 可执行回归与证据链，而不是宣称首次评测 agent trace。([arxiv.org](https://arxiv.org/html/2602.22769v2)) |
| **LoCoMo-Plus，2026** | 潜在用户约束、提示与相关记忆之间的语义间隔 | 在长期对话评测上加强隐式约束与触发关系 | 约束相关的回答正确性和一致性评估 | 提醒你：不能只换同义词；应加入“问题不直接提属性名，但任务确实需要该记忆”的样本。([arxiv.org](https://arxiv.org/abs/2602.10715)) |
| **StateMemBench，2026** | 随交互演化的当前状态、失效状态及关系依赖 | 多会话情境与可回放状态构造，使用闭集答案区分当前值和被覆盖值 | 当前状态正确率、旧状态错误等 | **事件账本、状态跟踪、旧值识别不是你的首创。**应借鉴严谨真值，避免把“最后一句覆盖”包装成一般推理能力。([arxiv.org](https://arxiv.org/html/2608.19652v1)) |
| **MemoBench 当前版** | 六类模板问答、词法干扰、策略差异 | 固定属性、固定句式、确定性生成 | 子串正确率、混合泄露率、上下文字符数 | 适合离线单元诊断；自然语言有效性、真实智能体、动作闭环尚待补充。依据本次源码复核。 |
| **MemoBench 建议版——目标，不是现状** | 记忆生命周期 + openKylin 任务复用 | 冻结的半合成多会话、显式证据账本、真实文件任务 | 分层评分、错误复用／遗忘后披露、任务完成率、成本与置信区间 | 差异化是**小型、可安装、可复现、可追责的开发者回归工具**，而不是覆盖面最大的学术基准。 |

另外，**MemoryBench、MemBench、MemoBench 是不同名称**。写相关工作时不要混用；MemoryBench 还包含持续学习和用户反馈驱动的评测设置。([arxiv.org](https://arxiv.org/abs/2510.17281))

### 一个特别值得吸取的最新教训

2026 年 10 月的一篇分析用冻结的“最后写入覆盖”规则重新检查 MemoryAgentBench 的冲突题，发现相当一部分分数可以由简单记账解释，并指出部分问题的发布答案与覆盖规则存在可达性问题。它是针对特定划分的分析，不能据此否定整个基准，但很适合提醒你的项目：

> **不要先给题目贴上“推理”“遗忘”的标签，再把分数直接解释成对应能力；先验证题目实际上需要什么，以及标准答案是否一致。**([arxiv.org](https://arxiv.org/html/2610.09193v1))

## A2. 主流记忆系统：机制、取舍与两天内接入价值

这里必须分清三种成本：**你的客户端依赖、被测服务的部署依赖、真实运行的模型调用成本**。用标准库发 HTTP，只意味着客户端轻，并不意味着整个系统“零依赖、零成本”。

| 系统 | 机制与取舍 | 两天内接入判断 |
|---|---|---|
| **mem0** | 从交互提取事实，执行新增／更新等操作，使用向量检索，可结合图记忆。灵活，但写入本身涉及模型、嵌入、异步处理和配置。平台 API 与 OSS SDK 不是同一条部署路径。([docs.mem0.ai](https://docs.mem0.ai/core-concepts/how-it-works)) | **已有服务时优先，未配置时不强求。**锁定版本，等待写入完成，每个故事独立 user/run，记录写入成本。当前适配器的存在不等于已接入成功。 |
| **Letta／MemGPT** | 经典路线是由智能体管理上下文内记忆和外部归档；当前 Letta 文档还提供 MemFS 等文件化记忆机制。因此必须注明到底测哪个版本，而不是笼统写“MemGPT”。([docs.letta.com](https://docs.letta.com/v1-sdk/memory/memory-blocks/)) | 服务已运行时，HTTP 适配可做；从零自托管不列初赛关键路径。较适合第二阶段做完整智能体比较。 |
| **Zep／Graphiti** | Graphiti 采用随时间变化的知识图谱和多种检索方式；Zep 是基于相关技术的托管产品，不能把两者结果混为一谈。([help.getzep.com](https://help.getzep.com/graphiti/getting-started/overview)) | 已有托管账户可小规模接入；**不建议两天内新搭图数据库和整套环境**。 |
| **LangMem** | 区分语义、情景和程序性记忆，并提供记忆维护与检索组件；可结合 LangGraph 等运行环境。灵活性高，但不是独立、无配置的通用记忆服务。([langchain-ai.github.io](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)) | 第二阶段更合适。初赛不要为增加一个名字引入另一套执行框架。 |
| **A-MEM** | 借鉴卡片式知识组织，生成带描述和标签的记忆，动态连接并调整已有记忆；写入与关联质量也受模型影响。([arxiv.org](https://arxiv.org/abs/2502.12110)) | 可研究，不建议从零复现进初赛主表。代理能写出“类似算法”，不代表忠实复现论文。 |
| **MemoryOS** | 分层管理短期、中期、长期记忆，包含存储、更新、检索与生成流程。这里的 OS 是记忆管理比喻，不是 openKylin 的系统组件。([arxiv.org](https://arxiv.org/abs/2506.06326)) | 适合作为第二阶段外部实现；初赛不应自行重写后冒用原系统名称。 |
| **ChatGPT Memory** | 官方说明涉及历史对话、保存记忆及其他可用来源；当前还有更新式记忆摘要。删除聊天、删除保存记忆、停止引用不是完全相同操作。内部实现不应自行推断。([help.openai.com](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)) | **不列自动化主榜。**本次未找到能让 MemoBench 直接、稳定调用消费端 Memory 的官方产品接口；普通聊天 API 不等于 ChatGPT Memory。 |
| **Kylin Agent Runtime／OpenClaw** | 属于完整智能体运行环境，能把跨会话记忆和后续动作放在同一条链路验证，最贴近命题。Kylin Agent Runtime 的官方仓库已经给出命令行入口；OpenClaw 提供会话与 agent 调用接口。([gitee.com](https://gitee.com/openkylin/agent-runtime)) | **优先做真实探测与接入。**初赛价值高于再接三个研究型记忆模块，但不能假设单次 CLI 调用天然具备正确的长期记忆行为。 |

特别注意 OpenClaw：当前文档区分 Gateway 与 `--local` 执行，后者会跳过部分可选的响应后工作。**不能为了调用方便选一种模式，再默认它与完整记忆维护行为等价。**要记录执行模式、会话结束处理及写入就绪条件。([docs.openclaw.ai](https://docs.openclaw.ai/cli/agent))

### 已证实的部分

| 方面 | 一手证据支持的情况 | 对项目的意义 |

### 本次未证实，不能写进作品当作已实现的部分

# B. 红队评审：当前项目哪里最容易被击穿

## B1. 源码复核后的判断

**当前项目不是没有价值，也不是“造假原型”。它是一个已经工作的受控测试工具，但现有分数的解释范围明显小于项目准备回答的问题。**

你的 README 已经主动披露规则摘要、合成数据、字符成本、未接真实助手等限制，这是优点。以下发现是对上传快照的实际复核，不是推测；对应代码位置、命令和原始输出见[审计记录](../02_execution_pack/AUDIT.md)。

| 问题 | 已发现的具体证据 | 严重性与处理 |
|---|---|---|
| **评分否定误判** | gold 为 UKUI，回答“不是 UKUI”仍正确 | P0。说明当前指标不是可靠的答案正确性判断。 |
| **拒答词可刷分** | “不知道，但你住在北京”能通过未知题 | P0。必须检查拒答后是否夹带无依据断言。 |
| **多字段关系丢失** | 编辑器、浏览器的值互换，只要两个词都出现仍通过 | P0。`answers` 平铺列表应升级为有键的答案结构。 |
| **错误复用与披露混淆** | “现在是 Vim，不再是 Emacs”被判错误且泄露 | 指标定义问题。合法历史否定不等于把旧值当当前值；真正隐私删除则可能连否定式披露也不允许。 |
| **缓存跨服务串用** | 相同模型名与 prompt，不同 `base_url` 读取同一缓存 | P0。会污染真实模型比较。 |
| **生成器与被测解析器耦合** | RuleReader 导入 `ATTRS`，多种策略共享相似语法假设 | 不是直接读取 gold，但属于结构耦合。只能解释为模板内诊断。 |
| **成本并不完整** | 写入在计时区间之外；没有 API usage、嵌入费用、存储成本 | 不能把 866→34 字符称为整体效率提高约 25 倍。 |
| **扩展与消融存在陷阱** | 40 轮设置触发采样异常；改变噪声会消耗共享随机流并改变故事 | 长度扩展要修；难度曲线应采用同故事配对。 |
| **“全上下文”并不包含所有角色** | 当前只保留 user 消息 | 引入真实助手和工具轨迹后，应改为完整角色历史，或者明确命名为 user-only。 |
| **缺少平凡基线** | 实测“始终回答不知道”在原数据上得到 **33.33%** | sliding_window 的 37.5% 必须放在这一背景下解释。 |

还有一个容易忽略的问题：**CPU 架构、系统版本、安装状态是环境事实，不应都当作可随意覆盖的偏好。**“我考虑换一台机器”“安装命令执行失败”“同事的设备架构”不能自动更新本机状态。源码里的 KARE 也不宜直接归类为包管理器；官方社区说明更接近软件兼容能力。([mailweb.openkylin.top](https://mailweb.openkylin.top/postorius/lists/?count=25&page=4))

# C. 深化方案

## C1. 总体架构：保留旧版，新增两条明确分开的评测路径

建议保留三种报告标签：

| 路径 | 评测对象 | 用途 |
|---|---|---|
| **Controlled / v1** | 原有模板 + RuleReader + 自制策略 | 单元诊断、CI、实现回归 |
| **Component / v2** | 自然语言历史 + 记忆组件 + 固定公共 LLM Reader | 在相同读取器下比较记忆选择与组织 |
| **Native Agent / v2** | 真实智能体自己的观察、维护、回答与工具执行 | 满足命题落地，评测整体行为 |

**三条路径不能混榜。**尤其不能给真实智能体取回一些文本，再让公共 Reader 替它回答，却把结果称作该智能体端到端成绩。

推荐数据流：

```text
事件账本 ──生成、校验──> 冻结的会话与环境输入
   │                          │
   │仅评测器可见              ▼
   └──> 标准答案/动作约束    被测记忆组件或真实智能体
                                 │
                                 ▼
                         回答 / 轨迹 / 文件产物
                                 │
                                 ▼
                  硬规则 + 语义裁判 + 少量人工复核
                                 │
                                 ▼
                    版本清单、分项指标、失败证据
```

事件账本是真值来源，不是发给被测系统的额外“提示答案”。

## C3. 怎样提高数据真实度，而不只是让分数变低

### 1. 先确定语义，再生成语言

不要让同一个 LLM 同时自由编造对话、自由生成答案，再由同一个 LLM 证明二者一致。

每个故事先写一个小型事件账本，例如：

```text
主体：本人
范围：项目 A
事件 1：默认报告目录设为 reports/old
事件 2：同事说自己的目录是 reports/team
事件 3：本人把项目 A 的目录改为 reports/new
事件 4：本人说“下个月可能再换一个目录”
查询：现在为项目 A 生成报告，应该保存在哪里？
```

正确答案是 `reports/new`。第二条不是本人状态，第四条是意向而非生效修改。

**阶段一只需要一个小型、可审查的状态规则，不要实现通用知识推理引擎。**

### 2. 让难度来自真实歧义的正确处理

| 扰动 | 建议样例 | 真值要求 |
|---|---|---|
| 隐式表达 | “你上次给我配置的那个输入法继续用。” | 前文必须有明确配置成功的证据 |
| 指代与省略 | “项目甲还是原来的，乙改到刚才那个目录。” | 主体和被指代目标必须唯一 |
| 同轮纠错 | “保存到旧目录……不对，这次以后都用新目录。” | 处理同一轮中的修正顺序 |
| 不同信息性质 | “考虑换”“已经换”“同事换了”“命令失败” | 意向、事实、他人事实、失败操作不能混用 |
| 作用域 | 工作机／家用机，项目 A／B | 不能全局覆盖一个同名属性 |
| 跨会话复用 | 新会话只说“按之前约定生成周报” | 应从历史恢复目录、模板等约束 |
| 遗忘与选择性保留 | 忘记虚构的门禁码，但保留报告目录 | 不能靠清空所有记忆通过 |
| 不充分证据 | “我平时用龙芯机器” | 没有足够设备信息时，不强制唯一架构答案 |

这里最后一个例子尤其重要：**你提出的“龙芯机器→loongarch64”不应直接成为可靠 gold。**应要求明确型号或系统输出，或者把题目设计成“不足以确定”。否则测试的可能是常识猜测，而不是记忆推理。

### 3. 采用“半合成”，不要冒充真实用户数据

初赛合理的表述是：

> 场景参考真实桌面工作流；数据为人工设计语义、模型辅助改写、人工核验后的合成数据。

保存生成模型、提示词、生成时间、原始响应、接受／拒绝理由和最终文本哈希。运行 Benchmark 时读取固定数据，不重新生成。

**建议审核量：**核对全部 60 个事件账本与问题；所有遗忘、冲突、边界题审核完整文本；其他文本至少抽查 25%。发现类别性错误，应回查整类，而不是只改抽中的一条。

### 4. 修正难度曲线

同一个故事使用独立随机源：

```text
story_seed → 核心事件和问题
surface_seed → 措辞
noise_seed → 干扰
```

用稳定哈希派生种子，而不是让同一个随机数流承担全部工作。

初赛只在 **12 个故事**上做 2K／8K／32K **字符**的配对扩展。实际调用的 token 数另从 API 获取。这样能回答“同一任务变长以后是否更容易错”，而不是比较三套不同题。

### 5. 防泄露与防刷榜：建立边界，不承诺做不到的事

初赛至少做到：被测系统不收到答案、命题类别、证据金标准；运行目录不包含私有 gold；开发／测试按故事和情节模板分开；公开 no-memory、always-abstain 和简单覆盖基线。

**仅改变随机种子不是可靠的防污染策略；仅改变 agent 工作目录也不是安全隔离。**本地有任意文件权限的 agent 可能读到同一主机其他目录。应使用受限工具、专用测试账户或隔离环境；做不到时明确威胁模型仅覆盖“避免意外泄题”，不声称能抵御恶意参赛者。

公开数据一旦用于排行榜，最终也会被针对性优化。第二阶段再增加维护方控制的留出集、轮换版本与提交限制，不能靠“数据开源但绝对刷不了榜”的说法解决。

## C4. 评分方案：让规则处理确定性，让 LLM 处理表达

### 1. 不再把正确答案存成无关系的字符串列表

建议答案结构至少支持：

```json
{
  "status": "answer",
  "facts": {
    "editor": "Vim",
    "browser": "Firefox"
  },
  "evidence_ids": ["e017", "e024"]
}
```

对于原生智能体，可以保留自然语言输出，再使用统一、冻结的解析或裁判流程；不能给不同系统定制不同宽松度。

路径、版本、数值应采用各自的规则。**Linux 路径不能统一转小写；`2.0` 和 `2.0 SP1` 也不能靠子串随意等同。**

### 2. 拆开几个现在混在一起的指标

| 指标 | 定义重点 |
|---|---|
| **答案正确率** | 正确的主体、字段、时间与值是否对应 |
| **旧状态误用率** | 在要求当前状态的题中，把过期值当有效值；分母是适用的更新题 |
| **遗忘后披露率** | 删除／禁止使用请求之后的新输出是否暴露受限内容；分母是适用遗忘题 |
| **未知信息乱答率** | 没有足够依据却作肯定断言 |
| **选择性保留率** | 遗忘目标信息后，无关有效信息是否仍然可用 |
| **任务完成率** | 文件、路径、内容与操作约束是否实际满足 |
| **证据支持率** | 可观察时，回答是否能追溯到有效证据；不可观察标 N/A |

“现在是 Vim，不再是 Emacs”可以是正确更新回答；但“我已经忘记你的密码是 123……”仍然披露了密码。**判断取决于用例的政策，而不是一套通用禁词表。**

### 3. 裁判提示词的核心结构

裁判只接收：任务定义、允许的证据、金标准、评分政策、候选回答。系统名隐藏，候选回答视为不可信数据。

要求输出：

```text
correct
supported_by_evidence
uses_superseded_value
discloses_forbidden_information
contradiction
error_type
evidence_ids
brief_reason
```

不要要求长篇自由发挥，也不要把裁判自己说的“置信度 0.95”当成经过校准的概率。

LLM judge 已知可能存在位置、篇幅和自偏好等问题，因此应做盲化、固定规范和人工元评估，而不是“换成强模型就可靠”。([arxiv.org](https://arxiv.org/abs/2306.05685))

### 4. 一个人也能做诚实的校准

建议 **20 个开发输出**调试规则和提示词，随后冻结；另取 **60 个留出输出**，覆盖系统、能力和易错类型，由你盲标。

报告：

\[
\text{一致率}=\frac{\text{人工与裁判判断一致的数量}}{N}
\]

同时计算 Cohen’s κ、混淆矩阵，尤其关注**错误放行率**。

本项目可以预先设定“留出一致率至少 90%、κ 至少 0.7”的内部门槛，但要明确这是**计划门槛，不是已经实现，也不是领域统一标准**。类别分布过于单一导致 κ 不可定义时应如实报告。

你只有一个人，因此只能称为**人工—模型一致性**，不能写成“多名人工标注者一致性”。两名代码代理也不能算两名人工。

### 5. 控制成本

规则能确定的结构化答案直接判；语义歧义才交给 judge，同时随机抽查一部分规则判定，避免规则错误完全漏检。

同一个主实验结果只判一次，裁判输出缓存并版本化。失败、截断、非法 JSON 单独记录。不要把裁判错误当记忆错误，也不要默默删除这些样本后只报成功部分。

## C5. 有说服力的端到端实验

### 模型选择

不追逐“最新最大”，优先**有权限、能固定版本、调用稳定**的模型。

| 用途 | 建议 | 注意事项 |
|---|---|---|
| 主读取模型 | DeepSeek API 的当前可用模型 | 本次官方文档使用 `deepseek-flash`，并说明部分旧名称路由到新模型。因此不要默认源码中的旧名称代表固定权重；保存请求名、返回名和日期。([api-docs.deepseek.com](https://api-docs.deepseek.com/)) |
| 第二模型复核 | Qwen 固定快照，例如文档列出的 `qwen3.5-flash-2026-02-23` | 选择可用快照是为了控制版本，不是宣称它最新；实际账户权限先探测。([help.aliyun.com](https://help.aliyun.com/zh/model-studio/qwen3-5-flash)) |
| 独立语义裁判 | 已有权限的 GLM 系列接口 | 先做校准，不默认更大就更准；不同版本参数支持可能不同，不能通用地强制关闭思考。([docs.bigmodel.cn](https://docs.bigmodel.cn/cn/guide/models/text/glm-5.3)) |
| 本地开源补充 | 已有 Ollama 环境下的 Qwen3.5 4B，或已经安装的固定模型 | 记录模型 digest、量化、上下文配置、Ollama 版本；客户端兼容只覆盖接口子集。没环境就放到第二阶段。([ollama.com](https://ollama.com/library/qwen3.5%3A4b)) |

### 初赛矩阵：控制在能解释清楚的范围

**主组件实验：**一个模型 × 96 个正式问答 × 四种策略。

四种策略建议是完整角色历史、BM25、当前 hybrid-template、空记忆。这里保留 hybrid 是为了观察其从模板到自然语言的泛化边界，不是继续把它优化成冠军。

**第二模型复核：**选择 12 个独立测试故事、两种表达，共 24 问，复核同样四种策略。

这部分合计：

\[
96\times4 + 24\times4 = 480
\]

次最终读取调用。**不包含数据生成、裁判、原生智能体内部工具循环和写入费用。**

**真实智能体实验：**Kylin Agent Runtime 与 OpenClaw，各运行 12 个生命周期故事。尽量同底模、同预算；不能一致时标记为整体系统比较。

**mem0：**已有可工作的服务才作为额外对照，不进入关键路径。

### 最值得做的消融

| 消融 | 回答的问题 |
|---|---|
| 空记忆／总是拒答 | 不使用记忆能拿多少分？ |
| 同语义、两种表达 | 结果是否依赖固定句式？ |
| 同故事、增加噪声或长度 | 难度变化是否真正影响同一任务？ |
| 完整有效证据直接给 Reader | 失败来自检索／保存，还是读取推理？此项只作诊断，不参加系统排名 |
| 移除关键历史证据 | 系统是否真的依赖记忆，而不是根据问题猜答案？ |
| 关闭历史保留／删除处理 | 相应能力是否真的依赖该机制？只对可控参考实现做，不篡改外部系统后仍冒用原名 |

### 统计与失败处理

主报告至少包含：独立故事数、问题数、重复次数、各能力分母、宏平均、微平均、超时／异常率、写入与读取耗时、可观察 token 用量。

置信区间以**故事为聚类单位**进行配对 bootstrap，例如固定统计种子做 2,000 次重采样。两个改写、同故事多个问题不能当成完全独立用户。

三个数据随机种子不等于三次独立模型运行。做模型重复时必须关闭回答缓存，且标记 repeat ID。初赛可以只对一个小子集重复；第二阶段再扩大。

**任务完成率应保留所有已安排任务的分母；内容正确率可另报有效回答上的结果，同时展示可用率。**不要因为某系统超时更多，就删除超时样本后宣称其更准确。

## C6. openKylin 落地方案的性价比

| 方案 | 价值 | 初赛建议 | 第二阶段 |
|---|---|---|---|
| **openKylin 真机／虚拟机 + CLI** | 直接满足运行环境要求 | **必须**，保存 `/etc/os-release`、架构、Python、程序版本与日志 | 增加第二配置，但不为数量盲目跨架构 |
| **两款真实智能体适配** | 直接满足演示要求，形成生态价值 | **最高优先级** | 加更多版本、重启与回归比较 |
| **实际文件／模板任务** | 将“记住”转成“做对” | **强烈建议**，限定测试目录 | 扩展项目级工作流 |
| **标准 JSON-over-HTTP／subprocess 协议** | 跨语言、接入成本低 | 先实现一种稳定传输，优先 subprocess 或现有 HTTP | 再补第二种和公开 SDK 示例 |
| **MCP server** | 便于提供受限任务工具或供开发者调用评测 | 非必须；不要手写整套协议赶工 | 使用官方 SDK 包一层，做协议一致性测试 |
| **本地 `.deb`** | 改善安装体验，契合建议项 | P1，核心完成后再做 | 完成安装／卸载测试与发布 |
| **软件商店上架** | 分发价值，但含外部审核 | **不承诺初赛完成** | 提交申请，记录真实进度 |
| **CI 回归** | 与开发者日常工作直接相连 | 离线测试必须；付费 LLM 手动运行 | 对接实际修复前后版本 |
| **排行榜网站** | 展示方便，但本身不是研究贡献 | 用已有静态 HTML 即可 | 静态发布 + PR 提交结果，无需账号系统 |
| **系统级记忆服务** | 与命题方向相关，但完全不同的工程规模 | **不要做** | 除非生态方提出明确需求，否则仍不做 |

**HTTP 不等于 MCP。**MCP 有规定的消息、生命周期和传输语义；当前正式规范列出 stdio 与 Streamable HTTP。初赛做一个自定义 JSON 接口，应诚实命名。([modelcontextprotocol.io](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports))

### 最推荐的实际演示场景

早期会话约定：项目 A 的周报存到旧目录，使用模板 v1。  
后续会话：用户修改目录与模板；同事信息构成干扰。  
新会话：用户只说“按之前约定生成本周空白周报”。

评测器检查**真实产物**：文件是否新生成、是否落在最新目录、模板是否正确、是否误用了同事配置、回答与动作日志是否一致。

不要提前由评测器创建正确输出文件，再让 agent “发现”它。输入夹具和待生成产物必须分开，比较运行前后文件状态。

再增加一个遗忘场景：使用明确虚构的 canary，删除后检查新回答／新文件是否披露，同时检查其他偏好仍可用。**这证明的是行为层可控，不自动证明数据库物理擦除。**

## C7. 能写进 PDF 的创新表述

建议用下面三句，前提是对应功能确实完成：

> **MemoBench 将跨会话对话、可观察记忆证据、动作轨迹和文件结果纳入同一评测流程，检查记忆是否被正确用于后续任务，而不只检查答案中是否出现关键词。**

> **通过显式状态账本与配对扰动样本，区分当前事实、历史事实、他人信息和未生效意向，并分别衡量错误复用、未知乱答与遗忘后披露。**

> **提供轻量 CLI 和 openKylin 智能体适配，使开发者能够在修改记忆实现后复跑同一组用例，查看可解释的行为回归。**

不要写“首次提出”“填补国际空白”“全面领先 LongMemEval”“零成本替代所有评测平台”。已有研究覆盖了状态跟踪、隐式偏好与行动轨迹，你的价值是**组合后的工程可用性和特定生态落地**。

### 开源治理的最小有效方案

代码继续使用现有木兰 PSL-2；自建数据明确独立许可证、来源和生成方式。外部数据按原许可处理，尤其不能把限制性数据集直接改成木兰许可证发布。PerLTQA 仓库的数据许可需要单独核对。([github.com](https://github.com/Elvin-Yiming-Du/PerLTQA))

数据版本至少保存 schema 版本、文本哈希、gold 版本、评分器版本、改动原因。修正 gold 后，旧结果应标记不再可比，而不是静默覆盖。

排行榜提交使用 PR：提交 manifest、配置、公开原始输出、结果摘要和许可证声明；区分**维护者复现**与**作者自报**。不要把付费调用或有凭据的自托管 runner 暴露给未经审查的 fork PR。

社区路径上，**先加入现有 AISubsystem／AgentOS／KylinBot 等相关协作，再讨论成为其测试项目**。官方有现成的 SIG 和仓库贡献流程；你无需先新建一个 SIG 才能贡献，也不能自行宣称已成为官方项目。([openkylin.top](https://www.openkylin.top/sig/application-cn.html))

## E2. 三分钟演示视频脚本

官方允许 3–5 分钟；以下按约 180 秒设计。网络耗时超过预期时，保留真实过程并控制在官方范围内，不把预录结果剪成“实时生成”。([bbs.openkylin.top](https://bbs.openkylin.top/t/topic/173541))

| 时间 | 画面 | 讲述重点 |
|---|---|---|
| **0:00–0:20** | openKylin 桌面、系统信息、MemoBench 版本 | “今天不是只测能不能背出一个值，而是检查改过的信息是否被正确用于新会话任务。” |
| **0:20–0:40** | 打开一个短故事及公开输入 | 展示早期目录、后续修改、同事干扰；不向被测 agent 展示 gold |
| **0:40–1:25** | 运行智能体 A 的短演示集 | 展示跨会话调用、实际工具动作与文件验证 |
| **1:25–2:10** | 对智能体 B 运行同一短演示集 | 强调相同输入、预算及已披露的配置差异 |
| **2:10–2:40** | 打开报告、雷达图与失败详情 | 从分数点进证据：是旧值误用、未知乱答、漏写文件，还是基础设施错误 |
| **2:40–3:00** | 原始结果、数据哈希、一键复现命令 | “离线诊断不需要密钥；真实智能体结果保留版本和原始证据。” |

提前跑完完整实验，视频只现场运行短演示集，再**明确标注**打开的是此前完整运行报告。若两个真实系统都做对了，就如实展示；可以额外展示标明“故障注入”的参考实现，不能假造竞品失败。
